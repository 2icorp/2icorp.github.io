## 답부터

로컬 커머스에 추천 모델을 붙일 때 **시맨틱 ID 설계에 위치를 넣지 않으면, 의미상 맞지만 도달할 수 없는 지점이 후보에 섞입니다.** 이것은 튜닝으로 없앨 수 있는 잡음이 아니라 코드 설계에서 비롯된 구조적 문제입니다.

## 시맨틱 ID가 하는 일

최근 추천 모델은 아이템을 정수 하나로 다루지 않고 **짧은 코드 열**로 압축합니다. 아이템 내용을 벡터로 만든 뒤 잔차 양자화를 층층이 걸어 코드 서너 개를 뽑고, 모델은 그 코드를 생성하는 방식으로 추천합니다. 아이템이 수천만 개여도 코드 사전만 들고 있으면 되니 파라미터가 크게 줄고, 새 아이템도 코드만 계산하면 즉시 다룰 수 있습니다.

문제는 이 압축이 **내용만 본다는 것**입니다.

## 로컬 커머스에서 무엇이 깨지나

서울의 치킨집과 부산의 치킨집을 생각해 봅니다. 메뉴가 같고, 카테고리가 같고, 리뷰에 쓰이는 단어가 같습니다. 내용 벡터로는 거의 같은 가게입니다. 그래서 같은 코드로 묶입니다. 실제 거리는 325킬로미터입니다.

일반 이커머스에서는 이것이 문제가 아닙니다. 배송이 전국이면 어느 창고에 있든 상관없기 때문입니다. 그러나 배달, 방문 정비, 지역 서비스처럼 **도달 가능성이 상품의 일부인 업종**에서는 같은 코드가 곧 같은 후보군을 뜻하므로, 추천 후보에 갈 수 없는 지점이 그대로 섞여 들어갑니다.

## 어떻게 쟀나

합성 POI를 만들었습니다. 여러 도시 군집을 지도 위에 뿌리고, 각 POI에 공통 카테고리 사전에서 뽑은 업종과 그 업종 원형에 잡음을 더한 내용 벡터, 그리고 자기 도시 안의 위경도를 줬습니다. 같은 업종이 모든 도시에 존재한다는 점이 핵심입니다. 이것은 저희가 만든 인위적 조건이 아니라 실제 로컬 카탈로그의 성질입니다.

그리고 코드를 두 방식으로 만들었습니다.

- **내용 전용**: 모든 층을 내용 벡터의 잔차 양자화로 만듭니다.
- **위치 인지**: 앞 층들은 동일하게 내용으로 만들고, **마지막 층만** 위치로 만듭니다. 위경도를 그대로 넣지 않고, 앞 층이 만든 묶음의 중심으로부터의 **거리와 방위**로 바꿔 넣습니다.

극좌표로 바꾸는 이유가 있습니다. 위경도를 그대로 양자화하면 격자가 지도에 고정되어 묶음 경계와 어긋납니다. 중심 기준 거리와 방위로 넣으면 "같은 음식인데 반대편 도시"는 갈라지고 "같은 음식에 같은 동네"는 붙습니다.

**공정성 조건이 하나 있습니다.** 두 방식이 만드는 코드 개수를 같게 고정해야 합니다. 위치 층을 그냥 덧붙이면 코드 공간이 커져서 버킷이 잘게 쪼개지고, 그러면 거리가 줄어드는 것이 위치 정보 덕분인지 단순히 버킷이 작아진 덕분인지 구분할 수 없습니다. 저희는 층수와 층당 코드 수를 양쪽에 동일하게 두었습니다.

## 결과

같은 코드를 공유하는 POI 쌍의 실제 거리를 하버사인으로 계산했습니다.

| 지표 | 내용 전용 | 위치 인지 |
|---|---|---|
| 같은 코드 쌍의 평균 거리 | 27.7km | 10.0km |
| 40킬로미터 초과 비율 | 24.2% | 0.3% |
| 배달 반경 5km 안 | 8.7% | 30.3% |

공개 POI 카탈로그 6만 곳의 실측값이고, 두 방식의 버킷 수를 맞춘 조건입니다.

## 도중에 걸린 함정: 코드북이 붕괴합니다

처음 비교했을 때 점유 버킷이 66개와 598개로 갈렸습니다. 버킷이 적으면 크고 크면 멀어지므로 그대로 비교하면 교란됩니다.

원인은 코드북 붕괴였습니다. 내용 전용 잔차 양자화가 실데이터에서 512칸 중 66칸만 씁니다. 문헌이 지적하는 실패모드가 그대로 재현된 것입니다.

그래서 양쪽 버킷 수를 맞춘 뒤 다시 쟀고, 여기서 더 강한 증거가 나왔습니다. 코드 수를 네 배로 늘려 점유 버킷이 40개에서 315개가 되어도 내용 전용 코드의 평균 거리는 27.9킬로미터에서 움직이지 않았습니다. **버킷을 아무리 잘게 쪼개도 지리는 좋아지지 않습니다.** 거리가 준 것은 위치 정보 때문입니다.

세 가지 독립적인 통제 방법으로 교차검증했고 감소폭은 56퍼센트에서 64퍼센트 사이였습니다. 매칭 조건에 따라 달라지므로 하나를 골라 인용하지 않고 범위로 적습니다.

## 무엇을 증명하지 않았나

**공개 POI 카탈로그이지 가맹점 데이터가 아닙니다.** 실측이지만 배달 플랫폼의 실제 가맹점 목록은 아닙니다. 실제 카탈로그는 도시별 밀도, 업종 분포, 배달 반경 정책이 전부 다르므로 반드시 다시 재야 합니다.

**저희 수치를 문헌 수치와 섞어 읽지 마십시오.** 로컬 서비스 추천을 다룬 선행 연구도 내용 전용 시맨틱 ID에서 같은 코드를 공유하는 지점의 절반 이상이 40킬로미터 넘게 떨어진다고 보고합니다. 저희 실측은 24.2퍼센트로 더 낮았습니다. 조밀한 대도시권을 쟀고 문헌은 국가 규모 설정이었기 때문으로 보입니다. 방향은 일치하고 크기는 다릅니다.

**빔서치와 추천 품질은 재지 않았습니다.** 이 글이 잰 것은 코드가 지리적으로 뭉치는가 하나뿐입니다. 그것이 최종 추천 지표를 얼마나 움직이는지는 별도 실험입니다.

## 그래서 무엇을 할 것인가

로컬 커머스에서 시맨틱 ID 기반 추천을 검토 중이라면 순서는 이렇습니다.

먼저 **현재 후보군에 도달 불가능한 지점이 얼마나 섞이는지 재십시오.** 같은 코드를 공유하는 지점들의 거리 분포와 배달 반경 안에 실제로 들어오는 비율, 이 두 숫자면 충분합니다. 대부분의 팀이 이 숫자를 갖고 있지 않습니다.

섞인다면 **코드 설계에 위치를 1급으로 넣으십시오.** 후처리 필터로 걷어내는 방법도 있지만, 그러면 모델이 애초에 도달 불가능한 후보를 만드는 데 표현력을 쓰고 필터가 그것을 버리는 낭비가 생깁니다.

그리고 **도달 가능성을 상시 점검 항목으로 심으십시오.** 코드북은 카탈로그가 바뀌면 다시 만들어야 하고, 다시 만들 때마다 이 성질은 다시 깨질 수 있습니다.
