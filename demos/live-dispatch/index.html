실제 OpenStreetMap 도로망 위에서 브라우저가 계속 계산하는 라이브 시뮬레이션입니다. 지도 데이터는 빌드 시점에 1회 내려받아 저장한 정적 파일이며, 이 페이지는 실행 중 외부로 아무 요청도 보내지 않습니다.

실제 지도 위 라이브 배차

강남·역삼·잠실·판교 4개 권역의 실제 도로망 위에서 음식점·주문·라이더를 배치하고, 주문이 계속 발생하는 동안 라이더가 도로를 따라 픽업과 배달을 오가는 모습을 그대로 봅니다. 배차는 최근접·번들·마감 우선순위를 쓰는 가벼운 휴리스틱이 매 틱마다 다시 계산합니다.

이 브라우저 데모의 배차는 경량 휴리스틱입니다(최근접 라이더 + 번들 적재 + 마감 우선순위, 픽업 전 주문은 원칙적으로 재배정하지 않다가 라이더 이탈 시에만 강제 재배정). 실제 랩이 쓰는 엔진은 OR-Tools CP-SAT two-phase 정수계획 solver이고, 그 solver의 실측 수치는 아래 "실측 카드"를 보세요. 위쪽 라이브 KPI는 전부 시뮬레이션 값입니다.

강남 권역

원은 식당, 작은 사각형은 배정 대기 중인 주문의 배달지, 점은 라이더(색이 옅고 점선 테두리면 이탈 처리 중)입니다.

식당 미배정 주문 라이더(가동) 라이더(이탈 처리 중)

실측 카드 (합성 데이터 실측, 실제 CP-SAT 엔진 결과)

위 라이브 지도의 숫자는 시뮬레이션 값입니다. 아래는 같은 배달 디스패치 문제를 실제 OR-Tools CP-SAT two-phase solver로 여러 규모에 걸쳐 실행해 잰 값으로, 권역급(중형 인스턴스, 주문 120·라이더 15) 규모에서 그리디 대비 즉시배정 성능과 라이더 이탈 후 재배차 성능을 각각 보여줍니다.

합성 데이터 실측(CP-SAT): 중형(주문 120·라이더 15) 인스턴스 3개 시드 평균. 그리디 대비 즉시배정 미배정 -21.8%·이동거리 -36.8% / 라이더 20% 이탈 + 서지 주문 10건 재편성 시 웜스타트 힌트가 cold 대비 변경 주문 -20.4%. 위 라이브 데모의 휴리스틱과는 알고리즘이 다르므로 숫자를 직접 비교할 수 없습니다. 어느 쪽이 나은지가 아니라, 가벼운 휴리스틱과 정식 solver가 같은 문제를 어떻게 다르게 푸는지를 보여주기 위한 참고값입니다.

정직하게 말하면

도로망은 실제 OpenStreetMap 데이터입니다(간선도로 primary/secondary/tertiary를 배차 경로 계산에 쓰고, residential 도로는 배경으로만 그립니다). 하지만 식당·주문·라이더의 위치와 발생 시점은 전부 시드 고정 합성 데이터이고, 실제 그 권역에 존재하는 가게나 배달 수요가 아닙니다. 라이더 이동은 실제 도로 그래프 위 최단경로를 따라가지만 신호·정체·일방통행은 반영하지 않습니다. 배차 로직은 매 틱 최근접 라이더에게 배정하는 가벼운 휴리스틱이라 실제 CP-SAT solver보다 품질이 낮고, 장시간 실행하면 미배정이 계속 누적될 수 있습니다(권역 하나의 라이더 9명이 감당하는 수요 상한을 넘기면 자연스럽게 나타나는 현상입니다). 지도 데이터 자체의 라이선스 표기는 페이지 하단을 참고하세요.
