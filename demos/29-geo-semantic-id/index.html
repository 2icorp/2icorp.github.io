브라우저에서 그 자리에서 계산하는 인터랙티브 데모입니다. 합성 데이터를 씁니다.

의미는 맞는데 갈 수 없는 가게를 추천합니다

최신 추천 시스템은 상품이나 매장을 콘텐츠 임베딩에서 뽑아낸 "시맨틱 ID"로 압축해 처리합니다. 배달·매장 방문처럼 위치가 중요한 로컬 커머스에서는 이 압축이 조용히 무너집니다. 서울의 치킨집과 부산의 치킨집은 콘텐츠상 거의 동일하지만 실제로는 300km 넘게 떨어져 있습니다. 위치 정보가 ID에 들어가지 않으면 시스템은 이 둘을 같은 묶음으로 보고, 갈 수 없는 가게를 추천합니다. 아래에서 같은 알고리즘을 콘텐츠만으로 돌린 경우와 위치를 더한 경우를 직접 계산해 비교합니다.

계산 방식. 매장마다 카테고리 원형벡터에 잡음을 더한 콘텐츠벡터를 만들고, 잔차 양자화(residual k-means, RQ) 방식으로 L개 층의 코드를 순서대로 뽑아 시맨틱 ID(K진법 L자리 코드)를 만듭니다. 콘텐츠 전용 방식은 모든 층을 콘텐츠벡터 잔차에서만 뽑습니다. 지리 인식 방식은 앞의 L-1개 층은 똑같이 콘텐츠에서 뽑되, 마지막 한 층만 다르게 뽑습니다. 같은 앞자리 코드를 공유하는 매장 그룹의 지리적 중심을 구하고, 각 매장이 그 중심으로부터 얼마나 멀리(거리) 어느 방향으로(방위각, 극좌표) 떨어져 있는지를 특징으로 다시 k-means를 돌립니다. 두 방식 모두 코드북 크기와 층 수가 같으므로 전체 ID 슬롯 수(K의 L제곱)가 동일합니다. 그래야 비교가 공정합니다.

매장이 모여 있는 도시 군집의 개수입니다. 도시가 늘수록 콘텐츠는 같아도 거리가 먼 매장 쌍이 늘어납니다.

참고 문헌(외부 보고, 우리 측정 아님)

로컬 서비스 추천을 다루는 연구에서는, 콘텐츠만으로 만든 시맨틱 ID를 그대로 쓰면 같은 ID를 공유하는 매장 쌍의 절반 넘게가 40km 넘게 떨어져 있다고 보고합니다. 이 수치는 이 데모가 계산한 값이 아니라 외부에서 보고된 문제의 방향성입니다. 위 지표 카드의 숫자는 전부 이 브라우저가 지금 계산한 합성 데이터 값이며, 방향은 같을 수 있어도 크기는 서로 다른 값입니다.

정직하게 말하면

이 데모는 실제 매장 데이터가 아니라 이 브라우저가 시드로 만들어낸 합성 매장으로 돌아갑니다. 실제 카테고리 임베딩, 실제 매장 좌표, 실제 사용자의 배달 반경을 쓰는 것이 아닙니다.

보여주는 것은 메커니즘과 개선 방향입니다. 콘텐츠만으로 시맨틱 ID를 만들면 지리 정보가 사라지고, 마지막 층에 위치 정보를 더하면 같은 ID 안의 매장들이 지리적으로 모인다는 구조 자체를 확인할 수 있습니다. 개선 폭이 정확히 몇 퍼센트라고 보장하는 것이 아닙니다.

실제 도입하려면 진짜 매장 카탈로그와 진짜 사용자 위치 분포로 다시 측정해야 합니다. 카테고리 분포, 도시 밀집도, 콘텐츠 임베딩의 실제 노이즈 수준이 이 데모의 가정과 다르면 개선 폭도 달라집니다.
